1. Background
The source design document (Procedure-1 & Procedure-
2) specifies a Zero-Trust, defense-in-depth architecture
connecting a private data center to public cloud,
spanning IAM, network segmentation, Kubernetes
micro-segmentation, hybrid connectivity, and
centralized monitoring. That document is an
architecture proposal, not a build artifact. This PRD
defines what needs to be
built — as code, policy, and
simulated infrastructure — to demonstrate the
architecture works, and how Google Antigravity's
agent-first workflow will be used to build it.
Core principle carried over from the design doc: a
compromised application must not automatically
become a compromised enterprise. Every requirement
below is written to make that principle testable, not just
described.

6. Functional Requirements
6.1 Network & Segmentation (maps to Doc §3,
§4, §6, §22, §23)
FR-1: Provision one Hub VPC (shared
services/transit/inspection) and ≥3 Spoke VPCs
(Student, Faculty/Exam, Research)
FR-2: No default transitive routing between Spoke
VPCs; cross-VPC traffic only via an explicit
inspected path

-- 6 of 15 --

FR-3: Each VPC has public (LB/ingress), private
(workload), and data subnets; data subnets have no
internet route
FR-4: Security groups default-deny; rules reference
source security groups, not open CIDRs, matching
the Doc §9 table exactly (Internet→Web:443 allow,
Web→App:8080 allow, App→DB:5432 allow,
Internet→DB:deny, Student VPC↔Exam VPC:deny,
App→K8s API:deny)
6.2 Hybrid Connectivity (maps to Doc §5, §22)
FR-5: Simulate the private-DC ↔ cloud link via IPsec
VPN with a firewall/inspection point on both sides
FR-6: Only required prefixes are routed across the
hybrid link (explicit route tables, not 0.0.0.0/0)
6.3 IAM & Zero Trust (maps to Doc §7, §24)
FR-7: Define least-privilege IAM roles for: application
developer, network engineer, cloud engineer,
Kubernetes engineer, security/SOC, admin
FR-8: Workload identity (no static credentials) maps
each K8s service account to one scoped cloud role
FR-9: Policy-as-code enforces no long-lived access
keys and blocks overly broad security-group
creation (permission boundary / org-policy
equivalent)

-- 7 of 15 --

6.4 Kubernetes Micro-segmentation (maps to
Doc §10, §23)
FR-10: One namespace per workload (student,
faculty, exam, research) with RBAC scoping
developers to their own namespace
FR-11: Default-deny NetworkPolicy per namespace;
explicit allow rules matching the Doc §10
allowed/blocked table
FR-12: Pod Security Standards set to Restricted (or
equivalent) on all namespaces
6.5 Monitoring & Attack Simulation (maps to
Doc §15, §14, §27)
FR-13: Central log sink ingests: security-group deny
events, K8s audit logs, auth events
FR-14: An automated test/script reproduces the
Section 14 scenario — simulate a compromised
research-app pod/credential — and asserts:
research DB reachable, Student-App/Exam-
App/Admin/K8s-control-plane unreachable
FR-15: Test output (pass/fail + evidence) is
captured as a build artifact (report), not just console
output

Working pattern in Antigravity:
1. Paste the relevant FR block (or the source design
doc section) as the task's objective/spec —
Antigravity performs best with concrete, verifiable
specs rather than vague asks.
2. Let the agent work asynchronously in its own space
(editor + terminal + browser) rather than only in a
chat sidebar; review its Artifact (plan + verification)
before merging, not just the diff.
3. Use the Agent Manager to run Phases 2, 4, and 5 as
parallel subagent tasks once Phase 1 scaffolding
exists, since they touch independent directories.

-- 12 of 15 --

4. Gate each phase's merge on its test/verification
artifact — do not proceed to the next phase until the
current phase's Artifact shows a pass.
5. Reserve the final Phase 8 task for cross-checking
the whole build against Section 14's attack scenario
and the FR table in this PRD, since that's the
architecture's core claim.

10. Assumptions & Open Questions

-- 13 of 15 --

Assumption: Build targets a single public cloud
provider for the implementation (recommend
picking one — AWS/Azure/GCP — even though the
source doc is multi-cloud in principle); confirm
which before Phase 2.
Assumption: "Private data center" is simulated (e.g.,
a local network namespace, second VPC, or on-
prem emulator) rather than physical hardware.
Open question: Should Cisco-specific tooling (ISE,
Secure Firewall) be mocked with equivalent open-
source/cloud-native tools (e.g., OPA/Gatekeeper for
policy, native cloud firewall for Secure Firewall) —
recommended, per Doc §16's own note that Cisco
products are optional.
Open question: Scope of "centralized logging" — a
real SIEM, or a lightweight stand-in (e.g., cloud-
native log service + a query dashboard) is sufficient
for demonstrating FR-13–FR-15.
